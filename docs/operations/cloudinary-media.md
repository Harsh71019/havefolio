# PER-12: private Cloudinary storage

The user-selected provider is Cloudinary. The server module, private storage adapter and forward attachment migration are implemented; **HTTP uploads and delivery are not enabled** while PER-7/8/13/14 remain dependencies. This is a storage foundation, not a completed photo/gallery journey.

## Configuration and privacy

Keep `MEDIA_STORAGE_ENABLED=false` until a dedicated Cloudinary product environment and runtime database connection are configured. Supply `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` and runtime-only `DATABASE_URL` through a protected server environment file. `.env.example` contains placeholders. Never use `NEXT_PUBLIC_` for credentials, put the Cloudinary URL/secret in an image, load a migration credential into the API, or enable an unsigned upload preset. Enabled media fails startup on incomplete/placeholder configuration. Disabled media makes no database/provider connection and manual API startup remains available.

All uploads explicitly use `authenticated`, `overwrite=false` and generated environment-scoped UUID keys. Images use the `image` resource; PDFs use `raw` with a generated `.pdf` suffix. Filenames remain in private PostgreSQL metadata and are discarded from Cloudinary upload metadata. Cloudinary receives original private content and a checksum context field; treat it as a third-party processor. Use distinct product environments/credentials for production and tests where possible. Prefix checks prevent accidental cross-environment key use; they do not restrict the account credential's provider permissions by themselves.

The adapter validates the returned identity, authenticated type, original size, format and image bounds; rejects provider errors with safe codes; and streams a bounded buffer without persistent CT media files. MediaService rejects empty/signature-mismatched input, unsafe filenames, images over 10 MiB and PDFs over 20 MiB, and caps active uploads at two per API process. These foundation checks are **not full image/PDF sanitisation**: complete decoding, decompression limits, EXIF stripping, PDF safety, per-owner/application quotas and attachment counts belong to PER-13/14 and must precede public route enablement. Multi-instance aggregate concurrency also needs coordination. Upload timeout is 30 seconds, with ambiguous writes left pending for cleanup.

`MediaService` exposes internal create/download/delete/reconcile methods through Nest dependency injection. It has no controller and no route accepting a caller-supplied owner header or body claim. Future controllers must derive owner UUID from the authenticated session and verify item ownership, use input DTOs, enforce multipart streaming bounds before buffering, and keep manual entry independent of media failure. The service already scopes metadata reads/updates to owner UUID; unknown, deleted or another owner's attachment returns `MEDIA_NOT_FOUND`. PER-7 adds the owner FK and optional item/owner FK; the verified identity must exist before inserting metadata. See [inventory domain](../architecture/inventory-domain.md) for identity shells, variant integrity and cleanup-before-erasure guards. Variants have parent linkage with an owner-matching composite FK; original creation is the only write exposed by this service until PER-13's variant pipeline.

Downloads use Cloudinary's time-limited authenticated API URL with a 60-second expiry, attachment disposition and SHA-256 signature. Permanent provider URLs are neither stored nor returned. Links can be replayed/shared within their TTL; never log them, use cache-control private/no-store and Referrer-Policy no-referrer in future delivery responses. Raw PDFs remain attachments, with no inline execution/preview in this foundation. Never substitute a non-expiring signed CDN URL without a separately reviewed access-control design. These API downloads are not CDN-cached and carry extra bandwidth costs per Cloudinary documentation.

## Metadata and failure recovery

Forward migration `0001_private_cloudinary_media.sql` adds `media_attachments`: owner, kind, filename, MIME, integer bytes, SHA-256 checksum, dimensions, environment-scoped object key, provider ID/version, parent/variant and timestamps. Constraints enforce supported types, sizes, states, checksum, dimensions and required provider identity before ready. Unique keys prevent overwrite/duplicate assets; owner/recovery/parent indexes bound queries. Self-reference is deliberately unqualified in the new SQL so it follows the migration search path, including isolated test schemas; original applied migration history is unchanged.

1. Persist a pending attachment before contacting Cloudinary. If that insert fails, no provider request occurs.
2. Upload to its new opaque key. Ready metadata follows only a matching successful provider response. Item associations in future tickets must reference only ready media.
3. On upload failure/timeout or an ambiguous ready commit, retain intent; do not delete immediately because the commit may have succeeded. A ready row is excluded from recovery.
4. Owner deletion first records deleting state, then destroys the authenticated exact object with cache invalidation, then records deleted. Failed provider/SQL steps preserve a retryable key. Provider "not found" is idempotent success. Deleted tombstones prevent access and retain exact keys for late/ambiguous writes; filenames, original checksums, dimensions and provider IDs are erased after confirmed deletion.
5. Internal `reconcile()` reads at most 20 pending/deleting/deleted rows older than 15 minutes, oldest first, and cleans exact objects. Compare-and-set on observed state/timestamp skips stale candidates if an upload completed or another worker claimed them. Deleted records are rechecked to catch late provider writes; do not prune tombstones before a reviewed retention policy proves provider finality. It returns counts only, with no contents/paths/errors. Originals with live variants are held until the variant deletion workflow exists.

Reconciliation is an implemented internal hook, **not a scheduled production job**. PER-13/40 must wire a bounded schedule/queue and monitoring before upload admission. Register it in one elected worker, keep cleanup retries idempotent and track pending age/recovery failures. Rechecking tombstones costs provider requests. Deleted rows retain an owner UUID and operational key/type/size fields, but no filename, original checksum or dimensions. PER-14/account deletion must define bounded tombstone retention and erase remaining owner links appropriately while preserving only minimal opaque cleanup keys when needed. No global provider deletion, cloud asset listing, directory sweep or database cleanup endpoint exists.

## Account setup, live verification and recovery gates

1. Create/select a dedicated Cloudinary environment; confirm intended region, retention and account permissions. No paid plan, add-on or account mutation is inferred.
2. Configure protected server credentials; validate account support for authenticated image/raw uploads and downloadable PDFs. Cloudinary may require account-level PDF delivery settings; do not silently publish assets to work around restrictions.
3. Use only synthetic media in a provider smoke: signed upload, exact authenticated result, unsigned original/derived URL denial, 60-second API delivery and expired-link denial, PDF attachment delivery, then approved exact fixture deletion/invalidation. This is unverified without credentials and account testing.
4. Apply the forward migration with the migration role through the existing explicit release process. The API receives only the runtime connection. No production migration was run by this implementation.
5. Back up PostgreSQL metadata and protected provider configuration; establish periodic encrypted exports of originals and a checksum manifest, deletion retention and a tested restore into a separate environment. Provider storage or backup features alone are not proof of coordinated app recovery. Export links are signed private capabilities, never public artifacts.
6. Monitor provider storage, bandwidth/transformation/API usage and billing alerts with agreed account limits. Avoid speculative transformations and cache public metadata only. Block uploads on quota/provider outage with a recoverable UI; manual entry continues. Seq receives safe reason/counter/correlation fields, GlitchTip sanitised unexpected failures, Gatus separate upload dependency readiness and ntfy deduplicated quota/failure/recovery alerts through later monitoring tickets.

PER-5's 10 GiB **local permanent-media** requirement is superseded for Cloudinary storage, not accepted at a lower threshold. PER-5 is deferred in Backlog, never Done. Its local evidence stays on its existing branch. CT disk/memory/CPU, transient buffers, image processing and database backup readiness remain PER-40 deployment gates.
