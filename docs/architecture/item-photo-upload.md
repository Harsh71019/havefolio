# PER-13: private item photos

The capture route is `/items/[itemId]/photos/new`; PER-11 links here after item creation. The API is rooted at `/api/v1/items/{itemId}/photos`. This ticket does not change the add-item form or implement the gallery/details UI. The return link uses the validated route item UUID, never an untrusted redirect. PER-18 supplies the full item destination. PER-23 can reuse `PhotoProcessor` and the private storage port after implementing desire ownership; no polymorphic desire schema is added now.

## Admission and processing

The existing session guard derives the owner and enforces the existing request-origin policy. Item ownership is checked before multipart parsing and again under the shared owner/item locks before reserving metadata. A caller cannot supply an owner field. Only repeated `photos` parts are accepted; text fields, extra file fields and more than four files fail. Files are at most 10 MiB, the complete multipart request (including overhead) at most 21 MiB, and receipt time at most 30 seconds. Content-Length and streamed byte counting both enforce the request limit. One capture request and one decoder run are admitted per API process; busy requests return 503. Multi-instance deployment must budget one process per replica and aggregate those budgets. No temporary filesystem is used. Abort, parser, validation, provider and database outcomes release buffers/admission; a disconnected client can have an unobserved successful save and must retry its Upload-Id to recover the result.

JPEG, PNG and WebP require matching declared MIME, filename extension and magic bytes. JPEG EOI, PNG IEND/chunk boundaries and WebP RIFF size reject truncation/trailing payloads; decoding with `failOn: warning` rejects corrupt pixel data. HEIC/HEIF brands in ISO-BMFF file signatures return `PHOTO_HEIC_UNSUPPORTED` even when named JPEG. Unsupported/ambiguous containers never reach the provider. PNG animation control and decoded multi-page/frame images are rejected. Embedded source metadata or otherwise ignored source payload is discarded by full decode/re-encoding; no original client bytes are persisted.

Sharp runs in a child process with a 128 MiB JavaScript heap, one native processing thread, no Sharp cache, maximum four channels, 8192 pixels on either axis and 24 million input pixels. The parent enforces a ten-second wall-clock deadline with SIGKILL (including metadata parsing); native operations also have an eight-second timeout. Decoded pixel limits, bounded source/output sizes, process admission and deployment memory limits bound native memory: the JavaScript heap setting alone is not an RSS limit. PER-40 must benchmark CT102 and enforce aggregate API/container memory/CPU budgets before release.

EXIF orientation is applied and all unnecessary EXIF/GPS/ICC metadata is stripped by default re-encoding. Deterministic WebP quality 85 variants fit inside 4096 (sanitized master stored as `original`), 1600 (`display`) and 320 (`thumbnail`) squares. Aspect ratio is preserved and upscaling is disabled. Dimensions, byte sizes and SHA-256 checksums come from processed output; the original private filename is replaced with `sanitized.webp` in metadata. [Sharp input safety](https://sharp.pixelplumbing.com/api-constructor/) and [image operations](https://sharp.pixelplumbing.com/api-operation/) define the decoder and orientation behaviours.

## Consistency, quotas and retries

Each request requires a UUIDv4 `Upload-Id` header. Each part's stable original UUID derives from that ID and its zero-based multipart index; variants get opaque UUIDs. Clients must retry the same ID with the same files in the same order. A matching ready original returns existing metadata without another provider write. Different processed content or owner/item scope cannot reuse an ID. Pending/deleting retries return `PHOTO_UPLOAD_PENDING`; after cleanup, `PHOTO_UPLOAD_RECOVERED` tells the client to allocate a new attempt ID. The capture UI sends one file per request, retains that file's ID across uncertain retries, and rotates it only after confirmed recovery. Selected files are not durably stored in the browser.

Under the existing owner/item transaction locks, reserve all three PER-12 pending records before any external upload. Existing composite foreign keys and triggers enforce owner/item/parent/purpose consistency. Provider keys are environment-scoped UUIDs; uploads use the server-only authenticated Cloudinary adapter with overwrite disabled. After all three provider calls succeed, one transaction marks the entire family ready, assigns application ordering and increments the item revision. No partly ready family can be published. Provider failure or an ambiguous SQL commit keeps exact-key intent; ready rows are never blindly removed. No provider identifiers/permanent URLs are returned in metadata. Authenticated access requests for a specific variant return a no-store, no-referrer capability expiring in 60 seconds through PER-12. That link is private and must not be logged or shared.

Admission limits are eight active photo originals per item, 2 GiB active stored bytes per owner and 4 GiB active stored bytes across the application. Pending/deleting data consumes quota until confirmed deletion. Owner locking prevents per-owner races; PostgreSQL advisory transaction lock 13130013 serializes global quota reservations across API instances. These are application/provider-storage quotas, not a waiver of PER-5's deferred local permanent-volume evidence. Raw source data never consumes permanent storage. Tombstones remain subject to the existing operator retention policy.

`GET photos` returns the current item revision and up to eight ready originals in `(position,id)` order. The first ready original is the cover. `PATCH photos/order` requires the complete ready-photo ID set and the last-seen item revision; moving an ID first selects its cover. Upload completion, reorder, cover and delete share owner locks and increment revisions. Pending completion takes its order after currently ready photos, so the first successful photo is the deterministic initial cover. Deleting the cover chooses the next `(position,id)` photo, or leaves an empty set. No separate competing cover model is introduced.

Delete requires the item revision. The original and all live variants become durably deleting in one metadata transaction before any provider cleanup, preventing partially deleted families from appearing ready. Variant then original cleanup uses PER-12 exact-key deletion/invalidation; provider failure keeps retryable metadata and retains the item revision. Retrying that revision completes the deleting family. Item erasure continues to use PER-10's cleanup and tombstone detachment rules.

## Recovery and deployment

When storage is enabled outside tests, the API runs a recovery tick every minute. PostgreSQL advisory transaction lock 13130014 elects one tick across replicas; each process also excludes overlapping ticks. PER-12 reads at most 20 pending/deleting/deleted candidates older than 15 minutes and uses state/timestamp comparisons. Variants settle first; an original blocked by variants is retried on a later tick. Deleted exact-key tombstones catch ambiguous late writes. No provider-prefix deletion, listing, shared-cache flush or unbounded filesystem cleanup exists. Structured recovery events contain counts or `RECOVERY_UNAVAILABLE` only, never provider errors, filenames, contents, URLs, SQL or credentials. Later Seq/GlitchTip integration can consume these bounded fields; provider budgets and tombstone retention remain operator responsibilities.

There is no new schema or migration: PER-7/10/12 already provide all required attachment relationships, positions, lifecycle states and revisions. Empty-state/repeat migration, drift/history, real isolated PostgreSQL/Valkey integration and mocked Cloudinary contracts remain required gates. No production service change, migration, deployment or live provider upload is performed. Keep `MEDIA_STORAGE_ENABLED=false` until protected provider configuration, unsigned-access denial, expiring access, deletion/invalidation, coordinated backup/restore and CT102 resource benchmarks are verified for the actual account.

The UI composes existing shadcn Button/Card/Input/Label primitives in the neutral light/dark themes and uses semantic progress/status/error elements. The approved [shadcn Input](https://ui.shadcn.com/docs/components/base/input) and [Kibo Dropzone](https://www.kibo-ui.com/components/dropzone) were inspected; native file inputs are appropriate for separate camera capture and gallery selection. Previews use revocable local object URLs, and network progress is distinct from server processing. Partial failure stays visible; confirmed photos are never re-uploaded on retry. Camera hints are browser/device-dependent; physical camera and assistive-technology behaviour still require release testing on real devices.
