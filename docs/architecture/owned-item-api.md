# PER-10: owned-item CRUD and lifecycle API

`ItemsModule` adds private, versioned endpoints using the global PER-8 session guard and `CurrentOwner`. Every item, relationship and history query includes the authenticated owner. Body ownership/identity/provenance fields and unsupported query parameters are rejected. Foreign and missing items return the same safe `404 ITEM_NOT_FOUND`. Responses are `no-store`; no attachment key, permanent URL, owner/session credential or database error is returned or logged.

| Endpoint | Result |
| --- | --- |
| `POST /api/v1/items` | 201 item and initial created event |
| `GET /api/v1/items?limit=25&after=<uuid>` | 200 bounded item page |
| `GET /api/v1/items/:id` | 200 current fields and immutable original entry |
| `PATCH /api/v1/items/:id` | 200 corrected item; required `revision` |
| `POST /api/v1/items/:id/actions` | 200 item with new history; required `revision` |
| `GET /api/v1/items/:id/history?limit=25&after=<uuid>` | 200 bounded event page |
| `DELETE /api/v1/items/:id` | 204 after erasure; body `{ "revision": 1 }` |

Minimal manual input is `{ "name": "Kettle", "ownershipStatus": "owned", "currency": "INR" }`. Currency is explicit because the approved schema requires it even for unknown price; clients may offer INR as their initial default. Missing/null `pricePaidMinor` returns null, while `"0"` remains zero. Amounts are decimal strings in integer minor units through the PostgreSQL bigint maximum; arbitrary triples, XXX/XTS, numeric JSON amounts, fractions and negative amounts are rejected. The approved checked-in current/historical ISO currency set remains authoritative; no conversions or spending calculations are introduced. Gifts retain an explicit paid amount when supplied and otherwise remain unknown.

`purchaseDate` is an object with `precision` and optional nullable `year`, `month`, `day`. Missing date means unknown. Unknown forbids components; year requires only year; month requires year/month; exact requires a valid Gregorian day, including leap-year rules. Components retain their precision and never default to today or the first day of a period. PATCH replaces this complete object rather than merging components. Null is accepted only for nullable money/details/taxonomy fields, not name, currency, date object, condition, frequency or tag array.

Creation preserves the supplied DTO representation (including supplied nulls and omitted fields) as immutable `original_entry`, with `original_source=manual`. Corrected snapshot values remain separate; details events identify user source, changed fields and revision. Condition/frequency changes also append their own events. Enrichment suggestions are never accepted or overwritten here. SQL constraints still enforce immutable original data. Name, strings, tags (50 unique IDs) and specifications (16 KiB serialized object) are bounded; the existing server-wide 16 KiB JSON request limit also applies and may reject combinations of large fields with 413.

Categories/subcategories/tags must exist for the owner; a subcategory requires its exact root. Newly assigned roots/children must be active. Existing retired assignments remain readable and unchanged assignments may accompany unrelated corrections. To clear a root that has a child, explicitly clear both. All item mutations use the same PostgreSQL owner-row transaction lock as PER-9 taxonomy writers. Tag removal now increments affected item revisions and appends details history before removing joins, just like category reassignment; clients cannot unknowingly overwrite taxonomy changes.

## Revision and actions

The existing positive integer `revision` is the concurrency token. PATCH/actions/delete require the client's last-seen revision. Snapshot updates atomically compare and increment the revision and check the affected row count; stale writes return `409 STALE_ITEM_REVISION`. Owner locking serializes simultaneous API writes across instances and taxonomy changes. Deletion also locks the item to block racing FK attachment associations. Delete/update races either complete deletion and reject the update with 404, or complete the update and reject deletion with 409. No last-write-wins fallback exists. A rejected retry writes no event; there is no separate idempotency-key convention in this repository. After an uncertain response, reload the item and its history before retrying an action.

Ownership changes use `action=ownership_changed` with `ownershipStatus`. Owned may transition to sold, donated, disposed, lost or returned. An inactive state may return to owned through an explicit recovery/reacquisition/correction action; direct inactive-to-inactive and no-op transitions return 409. This policy is recorded in PER-10's implementation notes. Historical purchase facts are untouched by every transition; returned does not create a refund or financial adjustment. Refund semantics remain PER-20/22.

`action=used` and `action=repaired` require currently owned, append occurrence history, and advance revision without changing condition, use frequency or ownership. An optional bounded note is private; explicit occurrence timestamps must be strict ISO dates with a timezone. Omitted occurrence time is the time the explicit action is recorded, not a purchase-date substitution. Repair does not imply replacement or automatically mark the item working.

Both collection endpoints use ascending UUID keyset order, with 1–100 records (default 25), `hasMore`, and a nullable `nextCursor`. UUID order is deterministic, not chronological. Times are returned for client presentation. Forward migration 0006 adds owner/item UUID indexes so pages do not sort an unbounded inventory/history. Pages are live views, not frozen exports: concurrent random-UUID insertions before a cursor can appear on a subsequent refresh. Full search/filter/custom sorting and inventory cards remain PER-17/16.

## Privacy erasure and provider recovery

Items are hard-deleted with cascading tags, warranties, suggestions and lifecycle history. No private original entry, notes or snapshot is kept in an item soft-delete table. Before provider calls, deletion verifies the current revision, all associated metadata, and no pending upload. Pending/over-capacity media returns `409 ITEM_MEDIA_PENDING`; reconciliation must settle pending provider writes before retry. Cleanup handles at most 500 metadata rows and processes variants before originals using the existing PER-12 `MediaService.delete` and exact-key provider deletion/invalidation. Manual records with no attachments remain deletable while provider storage is disabled.

Media progress uses separate durable PER-12 metadata transactions while the item transaction retains its lock. A provider or metadata failure returns 503, rolls back item erasure and preserves the original revision. Already deleted assets stay deleted, and deleting rows retain exact keys for retry/reconciliation. A failed deletion can therefore remove some media while retaining the item; reload and retry the same last-seen revision, or reconcile internally first. No provider failure is converted into successful erasure.

After every asset is confirmed deleted, the item transaction detaches scrubbed `deleted` tombstones and erases the item and dependent domain rows atomically. Forward migration 0005 replaces only the attachment guard to allow this narrow detachment when the complete original/variant family is deleted; live assignments, ownership, variant and purpose remain immutable. Detached tombstones cannot be rebound through a deleted-row update. Exact keys stay available to the existing bounded PER-12 recovery hook for ambiguous/late provider cleanup. This extends the prior restrict-until-cleanup policy without dropping references to live provider assets or purging recovery keys.

PER-12's operator-controlled tombstone/late-write retention policy remains in effect: no automatic pruning or new scheduler is introduced. Retained metadata contains opaque provider keys and scrubbed filename/checksum/dimensions, no private item payload. Live Cloudinary account deletion/invalidation, CDN denial and provider retention remain release verification work. Pending recovery and attachment admission must use owner locking/limits when PER-13/14 introduce upload routes. Large media sets make synchronous deletion slower; callers must reload/retry after timeouts and never assume an unobserved response means no cleanup occurred.

## Verification and release

Unit tests cover domain validation, DTO null semantics, safe failures and stale preflight checks. HTTP integration tests use disposable loopback PostgreSQL/Valkey, random per-run schemas/keys and a fake private storage provider, with real session authentication, transactions, constraints, concurrency and failure recovery. Existing suites test empty/repeated migrations, schema privileges, append-only events and live-media deletion guards. OpenAPI contract assertions cover request/response schemas, all endpoints and 400/401/404/409/503 errors.

Apply 0005/0006 with the migration role before rolling out this API. Review backups/locking and index creation for existing table sizes; no production migration or deployment is performed by this ticket. Prior SQL/snapshots/journal entries remain unchanged. No new environment credentials, service containers in production, queue, frontend page, upload flow, enrichment, resale estimate, financial aggregation or refund workflow is introduced. Existing authentication, private storage and telemetry redaction boundaries remain in force.
